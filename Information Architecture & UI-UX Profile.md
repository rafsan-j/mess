# Mess Manager

## Information Architecture & UI/UX Profile

**Document version:** 1.0
**Product version:** V1
**Related documents:** PRD v1.0, FRD v1.0, Non-Functional & Technical Requirements v1.0
**Platform:** Responsive web application
**Design direction:** Dark, minimal, functional, data-dense where appropriate
**Primary users:** Mess managers and mess members
**Primary device:** Smartphone
**Secondary devices:** Tablet and desktop
**Primary locale:** Bangladesh
**Currency:** BDT (৳)

---

# 1. Purpose

This document defines how Mess Manager should organize and present information to users.

It establishes:

* information architecture
* navigation
* visual hierarchy
* interaction principles
* manager/member separation
* responsive behavior
* component conventions
* form behavior
* table/grid behavior
* financial information presentation
* accessibility expectations
* loading/error/empty states

It does not yet define every individual page in implementation-level detail. That is the purpose of **Document 6 — Page-by-Page UI/UX Specification**.

---

# 2. UX Philosophy

Mess Manager is not a generic productivity application.

Its UI should communicate:

> **Operationally simple, financially precise.**

A manager should be able to enter data quickly.

A member should be able to understand their financial position quickly.

The interface should therefore prioritize:

```text
Clarity
  ↓
Speed
  ↓
Trust
  ↓
Detail
```

rather than decorative complexity.

---

# 3. Primary UX Principles

## UX-01 — Show the important number first

The user should not have to navigate through multiple pages to answer:

> How much do I owe?

or, for the manager:

> What is the current meal rate?

---

## UX-02 — Explain financial numbers

A total without a breakdown creates distrust.

Every significant financial total should have a path to its source.

---

## UX-03 — Separate "input" from "result"

Example:

```text
Meal entry
     ↓
Save
     ↓
Calculated result
```

The interface should make it obvious which values are entered by the manager and which are generated by the system.

---

## UX-04 — Reduce repetitive typing

Meal entry will potentially happen dozens of times per month.

The UI should optimize for rapid repetitive operations.

---

## UX-05 — Prevent destructive mistakes

The more consequential the action, the more explicit the confirmation.

---

## UX-06 — Do not hide important warnings

If settlement cannot currently be calculated correctly, the manager should see that immediately.

---

## UX-07 — Mobile first

The application should be designed for mobile interaction first, then expanded for larger screens.

---

# 4. Target Experience

The application should feel:

* modern
* minimal
* calm
* technical
* trustworthy
* slightly utilitarian
* fast

It should not feel:

* childish
* overly corporate
* playful finance-app
* visually crowded
* spreadsheet-like everywhere

---

# 5. Visual Direction

Recommended visual language:

```text
Dark neutral foundation
+
subtle elevated surfaces
+
restrained accent color
+
high-contrast typography
+
minimal borders
+
small-radius or moderate-radius cards
+
clear numerical hierarchy
```

A dark interface is appropriate for the intended visual direction, but usability takes priority over aesthetics.

A light theme may be added later if desired; V1 should maintain one coherent primary theme rather than designing two systems simultaneously.

---

# 6. Color Strategy

The exact palette should be finalized during visual implementation, but the semantic color system should distinguish:

### Neutral

Normal information.

### Accent

Primary actions and navigation emphasis.

### Success

Settled/successful state.

### Warning

Needs attention.

### Error

Invalid or blocked state.

### Credit

Money owed to the member.

### Due

Money owed by the member.

The system must not rely solely on color.

---

# 47. Read-Only Mode

When a period is closed:

* edit buttons disappear or become disabled
* forms become read-only
* a visible closed status appears
* explanations remain available

Do not make the screen look broken.

---

# 48. Warnings

Use a standardized warning component.

Example:

```text
⚠ Meal rate unavailable
There are no chargeable meals recorded for this period.
```

The warning should identify what action is necessary.

---

# 49. Blocker Presentation

For settlement closure:

```text
Cannot close period

2 issues need attention:

1. Internet allocation is short by ৳20.
2. No meals are recorded for 12 September.
```

Each blocker should, where possible, include:

```text
[Fix]
```

which navigates to the relevant workflow.

---

# 50. Success Feedback

Successful mutations should produce restrained confirmation.

Example:

> Payment recorded.

Avoid giant modal confirmations for routine operations.

---

# 51. Error Feedback

Errors should identify:

```text
What went wrong
+
What to do
```

Example:

> Payment could not be saved. Check your connection and try again.

---

# 52. Toasts

Toasts are appropriate for:

* successful save
* minor errors
* background status

They should not be the only presentation for major blocking financial issues.

---

# 53. Dialogs

Use dialogs for:

* confirmation
* deletion/removal
* manager transfer
* close period
* reopen period
* regenerate join code

Avoid dialogs for entire complex workflows on mobile where a dedicated page/sheet is easier to use.

---

# 54. Bottom Sheets

On mobile, bottom sheets are useful for:

* quick actions
* small filters
* transaction details
* member summary

Large multi-step forms should usually use a page or full-screen sheet.

---

# 55. Forms on Mobile

Full-width controls.

Avoid:

```text
two tiny inputs side by side
```

unless the fields are naturally related.

Example:

Amount may use a large touch-friendly input.

---

# 56. Input Types

Use semantically correct inputs:

* numeric keypad for money
* date picker for dates
* select/search for members
* segmented choices where appropriate

This reduces mobile friction.

# 58. Large Member Lists

If the mess becomes larger than the V1 target:

# 59. Search

# 61. Sorting

Default transaction sorting:

> newest first

This matches manager operational behavior.

---

# 62. Tables

Desktop tables should support:

* clear column headings
* right-aligned numerical values
* sticky headings where useful
* consistent row height
* hover/focus states

Financial values should align to improve scanning.

---

# 63. Numeric Alignment

Numbers should generally align right:

```text
৳1,250.00
  ৳850.00
  ৳120.50
```

This makes magnitudes easier to compare.

---

# 64. Cards

Cards should be used primarily for:

* summary metrics
* member records
* expense summaries
* alerts

Do not put every piece of content in a card.

Excessive cards produce visual fragmentation.

---

# 65. Spacing

Use a consistent spacing scale.

A compact data application should have restrained vertical spacing.

Manager workflows should not require endless scrolling.

---

# 66. Border Strategy

Borders should be subtle.

Use:

* separators
* active states
* input boundaries

rather than heavy boxes everywhere.

---

# 67. Icons

Icons should reinforce actions but should not replace important labels.

Example:

Good:

```text
[＋ Add Expense]
```

Less accessible:

```text
[＋]
```

---

# 68. Icon Consistency

Use one icon family/style throughout.

Avoid mixing multiple unrelated icon sets.

---

# 69. Animation

Animation should be subtle and functional.

Appropriate:

* navigation transitions
* expand/collapse
* save feedback
* loading indicators

Avoid:

* excessive motion
* decorative bouncing
* expensive background animations

---

# 70. Reduced Motion

Respect user/device reduced-motion preferences where possible.

---

Example:


# 79. Onboarding

First-time manager onboarding should be short.

Recommended:

```text

 ↓
Invite members
 ↓

 ↓

```

# 80. Onboarding Completion

Once setup is complete, normal dashboard behavior begins.

No persistent onboarding wizard should obstruct regular operations.

---

# 81. First-Time User Education

Use contextual helper text rather than long tutorials.

Example:

> Meal rate is calculated from meal-related food expenses divided by chargeable meals.

Only display detailed explanations where users may genuinely misunderstand the concept.

# 82. Financial Trust

Trust is a central UX requirement.

The application should visually distinguish:

```text
Recorded data
Calculated data
Finalized data
```

For example:

* "Recorded expenses"
* "Calculated meal rate"
* "Final settlement"

This distinction should be consistent.

---

# 83. Estimate vs Final

During an open month:

> Estimated current balance

may be appropriate.

After closing:

> Final balance

should be used.

Members should understand that an open month's figures can change.

---

# 84. Open-Period Member View

Display:

> Current balance

with explanatory text:

> This amount may change as meals, expenses, and payments are added or corrected.

---

# 85. Closed-Period Member View

Display:

> Final balance

and:

> This period was closed on [date].

---

# 86. Manager Settlement Language

Before closure:

> Estimated settlement

> Final settlement

# 88. Relative Dates

Relative labels such as:

may supplement, but should not replace, exact dates in financial records.

# 90. Settings UX

Settings should be grouped.

Recommended:

### Mess

* mess name
* join code

### Accounting

* meal types
* meal weights
* fractional meals
* guest rules
* rounding/configuration

### Management

* current manager / transfer

### Account

* profile
* password/security
* logout

Do not mix account settings with mess accounting settings.

---

# 91. Dangerous Settings

Actions such as:

* regenerate join code
* reopen period
* archive mess

should visually communicate consequences.

---

# 92. Role-Based UI

The application should render navigation and controls according to effective role.

But this is an experience optimization, not the security mechanism.

Database authorization remains authoritative.

---

# 93. Member Experience Constraint

The member should never feel like they are operating a spreadsheet.

Their primary question is:

> What is my current position?

The interface should answer that directly.

---

# 94. Manager Experience Constraint

The manager should never have to navigate through multiple pages merely to enter routine data.

The interface should optimize the common sequence:

```text
Meals
Expenses
Payments
Settlement
```

---

# 95. Information Density

Manager screens can be denser than member screens.

### Manager

Higher density.

### Member

Lower density, stronger explanation.

This is deliberate role-specific UX.

---

# 96. Desktop Density

On desktop, managers should be able to view a meaningful amount of information without excessive scrolling.

---

# 97. Mobile Density

On mobile, hierarchy should replace density.

Show:

```text
Most important
 ↓
Secondary
 ↓
Details on demand
```

rather than fitting everything simultaneously.

---

# 98. Progressive Detail

Use:

```text
Summary → Detail → Source
```

Example:

```text
Amount due ৳507
      ↓
Statement breakdown
      ↓
Individual expense allocations
      ↓
Original expense
```

This is a core information architecture pattern.

---

# 99. Navigation Back Behavior

After editing an expense:

Returning to the expense list should preserve:

* current period
* current filter
* current scroll position where practical

This reduces repetitive navigation.

---

# 100. State Preservation

The app should preserve appropriate temporary context:

* selected date
* selected period
* filters
* search text

but should not preserve sensitive unsaved financial records as though they were saved.

---

# 101. Confirmation Language

Confirmation copy should state the consequence.

Bad:

> Are you sure?

Good:

> Close September 2026? The period will become read-only and its settlement will be finalized.

---

# 102. Destructive Wording

Use direct verbs:

```text
Remove member
Reject request
Regenerate code
Reopen period
Close period
```

Avoid vague verbs such as:

```text
Proceed
Continue
Action
```

for consequential operations.

---

# 103. Undo

For some low-risk UI operations, undo may be useful.

For financial transactions, do not rely on a transient undo toast as the sole recovery mechanism.

Use explicit correction or edit workflows.

---

# 109. Accessibility — Labels

Every form input must have an explicit accessible label.

Do not depend solely on placeholders.

# 110. Accessibility — Focus

Interactive elements require visible focus.

# 111. Accessibility — Tables

Tables should have semantic headings.

Important mobile transformations must preserve understandable relationships between labels and values.

# 112. Accessibility — Errors

Validation errors should be associated with the relevant field and understandable without color alone.

# 113. Accessibility — Status

"Due", "Credit", "Settled", "Closed", etc. must be represented in text.

---

# 114. Accessibility — Touch Targets

Interactive elements should be comfortably tappable on mobile.

---

# 115. Accessibility — Motion

Do not rely on animation to communicate critical state changes.

---

# 116. Accessibility — Contrast

Primary text and important numerical values should maintain adequate contrast against their backgrounds.

# 117. UX Treatment of Financial Errors

Financial errors require stronger feedback than ordinary form errors.

Example:

```text
Cannot close period

Expense allocation mismatch:
Internet · Difference ৳20.00

[Review expense]
```

This should receive more attention than a minor profile validation error.

---

# 118. Security UX

Security should be visible without becoming obstructive.

Examples:

```text
This period is closed.
```

```text
Only the manager can edit this data.
```

These messages explain why something cannot be changed.

---

# 119. Permission Error UX

When a user somehow reaches an unauthorized operation:

> You don't have permission to perform this action.

Do not expose internal policy details.

---

# 120. Network Error UX

Show:

> You're offline or the connection was interrupted.

and, where appropriate:

> Your data was not confirmed as saved.

Avoid claiming failure when the final state is genuinely unknown.

---

# 121. Retry UX

Retry actions should be explicit.

For example:

```text
Couldn't load payments.

[Retry]
```

For financial writes, duplicate-safe behavior must be established before encouraging repeated submission.

# 122. Unsaved State

Forms should communicate:


when appropriate.

# 123. Save State


when a more precise status is possible.

# 154. Interaction Cost

For frequent tasks, optimize for low interaction count.

Meal entry should require as few:

* taps
* modal transitions
* page loads
* repeated selections

as practical.

# 155. Manager Efficiency Principle

If a manager has to enter:

```text

×

×
```

# 156. Member Simplicity Principle

Members should not be exposed to the complexity required to maintain the mess.

Their default experience should feel closer to:

> Personal financial dashboard

than:

> Accounting control panel

Example:


# 158. Trust Through Consistency

The same total displayed in:

* dashboard
* statement
* settlement
* history

must match.

Different rounding or calculation behavior between screens is unacceptable.

# 159. UX Rule for Calculated Data

Calculated numbers should not look like editable inputs.

# 161. Preventing Accidental Edits

Read-only calculated values should not respond to ordinary input patterns.

# 163. Core UX Flow

The ideal manager loop is:

```text
Home
 ↓
Record today's meals
 ↓
Add expense if needed
 ↓
Record payments if received
 ↓
Dashboard automatically updates
```

No manual "recalculate" action should exist.

---

# 164. No Manual Recalculation Button

The user should never see:

> Recalculate meal rate

as a standard operation.

The application calculates automatically.

A technical recalculation function may exist internally.

---

# 165. No Manual Settlement Calculation

Likewise, the manager should never be required to type:

```text
meal rate
member cost
shared cost
```

as derived values.

---

# 166. Manager Confidence Loop

After entering a financial transaction:

```text
Save
 ↓
Confirmation
 ↓
Updated totals
```

The manager can immediately see its effect.

---

# 167. Member Confidence Loop

After a new payment:

```text
Payment recorded
 ↓
Current balance updated
```

The member's statement should reflect the new state after server confirmation.

---

# 168. Performance Perception

The UI should communicate progress during slow operations.

For example:

```text
Calculating settlement…
```

is preferable to an unresponsive screen.

---

# 169. Error Recovery

Where possible, error states should include an action:

```text
[Retry]
[Review]
[Go to expense]
```

rather than forcing users to determine the next step themselves.

---

# 170. Navigation Safety

When a financial form contains unsaved changes:

```text
You have unsaved changes.
Leave without saving?
```

---

# 171. Data Context

Every accounting page should make the period clear.

Example:

```text
Expenses
September 2026
```

Never leave the user guessing which month they are modifying.

---

# 172. Date Context

Meal pages should clearly display:

```text
Thursday
10 September 2026
```

rather than merely:

```text
10/09
```

when ambiguity might exist.

---

# 173. Currency Context

The current currency can be represented in the application context, but financial inputs should still clearly identify monetary units where ambiguity is possible.

---

# 174. Member Identity

Use the member's preferred display name.

Do not overexpose email addresses in everyday accounting screens unless necessary.

---

# 175. Privacy-Oriented Member List

For ordinary member-facing screens, use display name rather than email where possible.

---

# 176. Manager Financial Overview

Manager can see:

* all members
* all balances
* all transactions

because this is required for the manager's accounting role.

---

# 177. Member Financial Privacy

Member should not see other members' detailed balances by default.

Aggregate mess-level figures may still be shown where appropriate.

---

# 178. Audit Privacy

Members should not access internal audit records by default.

Managers can access them.

---

# 179. Join Request Privacy

A prospective member should see their own request state.

They should not see the identities of unrelated pending applicants.

---

# 180. Settings Security

Sensitive account/security operations should be separated from mess-management controls.

This helps users distinguish:

```text
My account
vs
Mess administration
```

---

# 181. Visual Tone

Use subtle visual personality through:

* typography
* spacing
* small accent details
* restrained iconography

rather than decorative illustrations on every screen.

---

# 182. Empty State Illustrations

Not required.

Simple typography and a small icon are preferable to large decorative graphics.

The UI should aim for WCAG 2.1 AA-oriented implementation.

Critical operations must remain usable without a mouse.

# 186. Core UX Rule Set

The UI implementation must preserve these principles:

```text
1. Current period is always obvious.
2. Current role is always implicit/clear.
3. Important financial values are immediately visible.
4. Derived values are visually distinguishable from inputs.
5. Members cannot be presented with management actions.
6. Closed periods look intentionally read-only.
7. Every important amount can be explained.
8. Frequent manager workflows are optimized for speed.
9. Mobile is treated as a first-class interface.
10. Color never carries meaning alone.
11. Financial errors receive prominent treatment.
12. The interface never asks the manager to manually recalculate.
```
